О документе

Продолжение истории после версии 0.1.15. Версия 0.1.16 закрывает эксплуатационную проблему, выявленную на рабочем сервере: после апгрейда ОС (Ubuntu 20.04 → 22.04, системный Python 3.8 → 3.10) виртуальное окружение .venv перестало запускаться — прежний интерпретатор исчез, служба не стартовала, сайт отдавал ERR_CONNECTION_REFUSED. Теперь скрипты обновления сами обнаруживают и устраняют это.

Версия 0.1.16 — самовосстановление окружения при обновлении Python

Скрипты обновления (scripts/linux/update.sh и scripts/update.ps1) теперь в начале проверяют, действительно ли запускается интерпретатор из .venv. Если окружение сломано или отсутствует — оно пересоздаётся, ставятся зависимости, приложение перезапускается.

  • Срабатывает даже без новых коммитов — поэтому ближайшее ночное авто-обновление само поднимет сервер после апгрейда ОС/Python, без ручного вмешательства.
  • Данные (base.db, резервные копии, логи) не затрагиваются — пересоздаётся только виртуальное окружение.
  • Логика симметрична на обеих платформах: Linux (Bash/systemd) и Windows (служба NSSM или задача Планировщика).

Этапы разработки (0.1.16)

0.1.16Самовосстановление .venv в скриптах обновления

  • ДОБАВЛЕНО Проверка работоспособности .venv (реальный запуск интерпретатора) в начале обновления; при поломке — автоматическое пересоздание окружения и переустановка зависимостей.
  • ИСПРАВЛЕНО После апгрейда ОС/Python приложение больше не остаётся «лежать»: служба (Linux systemd, Windows NSSM) или задача Планировщика перезапускается автоматически, в том числе при отсутствии новых коммитов.
  • Сохранены защитные механизмы: резервная копия базы перед обновлением, откат кода при ошибке, корректные права при запуске от SYSTEM/root.
  • ДОКУМЕНТАЦИЯ Создан changelog выпуска 0.1.16; версия приложения поднята до 0.1.16 и отображается в интерфейсе.
